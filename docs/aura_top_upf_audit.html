The headline result: this app's own elaborator cannot read this file at all. It fails on line 19, the second command. Walking the file by neutralising each rejection in turn — the method used to collect the evidence below — it never reaches the end: 7 commands are not registered and 6 flags on registered commands are rejected.

That is not the same as the generator being broken, and the two are kept separate throughout. Where the app generates a construct correctly but cannot read the reference's spelling of it, that is an importer tolerance gap, not a generation bug.

One finding settles an open question from earlier today. The Name Prefix work left set_isolation -name_prefix unverified — absent from all five published option lists checked, so it was deliberately not emitted. This file uses it six times (L309, 319, 331, 343, 357, 369). That is real-world usage evidence I did not have, and it is the strongest argument yet that the flag is genuine. It does not by itself prove LRM membership, so it stays flagged — but it materially changes the balance.

Power domains L35–40

create_power_domain PD_TOP    -include_scope

Six domains. Five use -elements and are fully supported. PD_TOP uses -include_scope (“this domain is the current scope”) — rejected by the elaborator. Confirmed real: a published example writes create_power_domain pd_DEC -include_scope. The app already has the concept (it writes a root-level domain as -elements {.}), so this is a parse gap, not a model gap. b

Supply ports and nets L46–83

ConstructUsesFindingClass

create_supply_net X -domain PD -reuse10Rejected: “supply net already exists at scope”b
connect_supply_net X -ports {X}6Supported; the app emits this sectiona

The -reuse rejection is a defect in this project's own most recent work. The flag was added two commits ago and is accepted by the parser — but the duplicate-name check runs first and fires, because this file scopes nets by -domain rather than by set_scope, leaving every net at scope "". So create_supply_net VDD_AON -domain PD_CPU -reuse collides with the root VDD_AON and the file is rejected.

This is precisely the construct that means “this is the same net, continued”. Rejecting it as a duplicate inverts its meaning.

Power switches L116–145

create_power_switch SW_CPU \
  -domain              PD_CPU \
  -input_supply_port  {vin  VDD_TOP} \
  -output_supply_port {vout VDD_CPU} \
  -control_port       {sleep_n pwr_en_w[2]} \
  -ack_port           {ack     pwr_ack_w[2]} \
  -on_state           {on_state  vin {sleep_n}} \
  -off_state          {off_state    {!sleep_n}}

map_power_switch SW_CPU -domain PD_CPU -lib_cells {HDR_X16 HDR_X8}

Three switches, structurally identical apart from domain, rails and control-bit index. create_power_switch is fully supported on every flag, -ack_port included — which was added earlier today, and this file independently confirms both its existence and its {port net} shape. a

Two problems on the mapping command: -domain is rejected b, and -lib_cells {HDR_X16 HDR_X8} carries two cells where the app keeps only the first b. The switch name is positional here, matching the correction made earlier today.

Supply-set power states L151–181

add_power_state SS_TOP -supply \
  -state HV  {-supply_expr {power == {FULL_ON $DVDD_NOM} && ground == {FULL_ON 0.00}}} \
  -state LV  {-supply_expr {power == {FULL_ON $DVDD_LOW} && ground == {FULL_ON 0.00}}}

Seven commands, 19 states. Two independent problems, both rejected:

  • The bare -supply marker. The object name is positional and -supply is a bare marker meaning “the object is a supply set”. The app registers -supply as taking a value, so it swallows the following -state and the parse collapses. Measured directly: add_power_state -supply SS -state {…} works, add_power_state SS -state {…} works, add_power_state SS -supply -state {…} fails. b
  • The split -state NAME {flags} form. The app expects the name inside the group (-state {NAME -supply_expr …}), which is the LRM's own signature. The reference puts the name outside. Both forms occur in published material, so this is a tolerance gap, not a reference error. b

add_power_state SS_MEM … -state RET {-supply_expr {power == {ON $MVDD_RET}}} (L171) uses the state type ON, which is not one of the four values this app's redesigned vocabulary admits (FULL_ON / PARTIAL_ON / OFF / UNDETERMINED). The importer's fallback silently reinterprets an unknown token carrying a level as FULL_ON, so this arrives as FULL_ON 0.60. b uncertain

Domain power states L187–243

add_power_state PD_CPU -domain \
  -state RETAIN  {-supply_expr {SS_CPU == OFF && SS_RET == ON} \
                  -logic_expr  {iso_en_w[2] == 1}}

add_power_state PD_TOP -domain \
  -state PS_TURBO {-supply_expr {SS_TOP == HV} \
                   -logic_expr  {PD_CPU == RUN_HV && PD_DSP == RUN_BOOST && …}}

Six commands, 25 states — and structurally the most important thing in the file. Each per-domain state names a condition over its supply sets' states; PD_TOP's seven states then compose the other five domains' states into the system modes the RTL sequencer walks (aura_pmu_pkg::power_state_e uses the same names).

This app has no data model for it at all. PowerState.domain is classified UNMODELLED with the reason “a power state is attached to a supply here, never to a domain directly”. The Power State Table models one flat table of per-net values; it has no notion of a domain-level state, nor of one state's expression referring to another state by name. c

  • add_port_state, 9 uses — not registered, no model. Three of them take a switch output port (SW_CPU/vout) as the state object. c uncertain
  • create_pst / add_pst_state — registered and importable. set_retention RET_CPU_RF \

  -elements            {u_cpu/u_core/u_rf} \
  -retention_supply_set SS_RET \
  -save_signal         {ret_save_w[2] posedge} \
  -restore_signal      {ret_restore_w[2] posedge} \

  -restore_signal {ret_restore_w[2] high} \
  -assert_r_mutex {ret_save_w[2] high ret_restore_w[2] high}

map_retention_cell RET_CPU_RF -domain PD_CPU -lib_cells {RSDFFQ_X1 RSDFFQ_X2}

Two strategies. The core — domain, elements, retention supply set, save/restore — is supported. Three things are not:

  • The edge/level half of the signal pairs. {ret_save_w[2] posedge} is a pair; the app models save/restore as a single free-text string, so posedge (and set_retention_control's high) has nowhere to live. c
  • -retention_condition {!pwr_en_w[2] || iso_en_w[2]} — no field, no boolean-expression editor. c
  • -assert_r_mutex — a save/restore mutual-exclusion assertion. No model. c
  • map_retention_cell, 2 uses — not registered, and RetentionStrategyPlacement has no cell_type field. c

Fourteen connect_supply_net calls in total, eight of them generated by a Tcl foreach. The command and the hierarchical pin-path form are supported — this is exactly the shape the app's own “Macro Connections” section emits. a

Flagged uncertain

Surfaced rather than silently resolved, per the audit's own rules.

  1. set_isolation -name_prefix — used 6× here; absent from all five published option lists checked. Real-world evidence now points strongly to it being genuine, but LRM membership is unconfirmed. This is the one item where access to the actual standard would change a decision already taken today.
  2. map_power_switch -domain — the other three map_*_cell commands take -domain as a required argument, confirmed against a signature reference. For map_power_switch specifically I found no signature that includes it, and one tool reference that omits it. The file's consistency across all four argues it is right.
  3. set_related_supply_net — no reference found. Possibly UPF 1.0-era.
  4. The supply state name ON (L171) — the standard supply-state vocabulary is FULL_ON / PARTIAL_ON / OFF / UNDETERMINED. Whether ON is a legal alias, a user-defined name, or an error in the reference is unresolved; the app currently reinterprets it as FULL_ON without saying so.
  5. add_port_state on a switch output port (SW_CPU/vout) — plausible and internally consistent with create_pst -supplies listing the same paths, but unverified.

What this does not claim

The audit tested the elaborator against the file empirically, and compared the generator to it by tracing code and checking the feature classification. It did not test whether the RTL resolver can match this file's hierarchical paths against the elaborated aura_top design — the escaped generate-block brackets and dotted generate labels in section 11 are the obvious risk there, and that is a separate exercise.

Nor does it propose implementations for anything in category (c). Several of those — domain power states and the transition graph in particular — are large enough to be product decisions rather than features, and one (-assert_r_mutex) may be correctly out of scope given this project's stated “not signoff-grade verification” boundary.

Phases 1–3 only. No code changed. Category (b) fixes await review of this report; category (c) items await a separate decision.
