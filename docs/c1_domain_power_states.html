Audit item C1 · Research and proposal · No code changed

Domain Power States

A power domain whose named states are written in terms of other domains' named states. What the reference file actually says, why the current two-tier model cannot hold it, and three ways forward — with the honest cost of each.

examples/aura_top/upf/aura_top.upf · section 6, L183–243 · 6 commands, 22 states

One thing found while measuring, before any of the design discussion. Eighteen of the 22 domain states carry BOTH a -supply_expr and a -logic_expr. The IR has a single PowerState.expr field, and _nested_state_expr() is documented as returning “the first -supply_expr/-logic_expr value found” — so one of the two is silently discarded.

Measured on PS_TURBO: the IR keeps SS_TOP == HV and loses PD_CPU == RUN_HV && PD_DSP == RUN_BOOST && … entirely — which is the whole of what C1 is about. This is a backend defect below the GUI, it applies to all three options below, and it is worth fixing on its own terms regardless of which one is chosen. The phase-1–3 audit missed it because that audit measured what got rejected, not what got silently dropped.

1. What the reference actually says

Quoted from the file, not from the earlier audit. Section 6 contains two structurally different things, both written with the same command.

Layer A — leaf domain states L187–211 · 5 commands, 15 states

add_power_state PD_CPU -domain \
  -state RUN_HV  {-supply_expr {SS_CPU == ON_HV} -logic_expr {iso_en_w[2] == 0}} \
  -state RUN_LV  {-supply_expr {SS_CPU == ON_LV} -logic_expr {iso_en_w[2] == 0}} \
  -state RETAIN  {-supply_expr {SS_CPU == OFF && SS_RET == ON} \
                  -logic_expr  {iso_en_w[2] == 1}} \
  -state DOWN    {-supply_expr {SS_CPU == OFF} -logic_expr {iso_en_w[2] == 1}}

What it expresses. “PD_CPU is in state RUN_HV exactly when its supply set SS_CPU is in its own state ON_HV, and the RTL signal iso_en_w[2] is 0.” The two clauses are different kinds of condition, which is why UPF gives them separate flags: -supply_expr is a condition over supply-set states (Tier-1 names), -logic_expr a condition over RTL logic.

RETAIN is the interesting one: its -supply_expr conjoins two supply sets, and the second (SS_RET) is not PD_CPU's primary — it is its default_retention handle, associated at L109. So a domain state can be a condition over any supply set the domain is associated with, not just its primary.

Layer B — the composite system state L215–243 · 1 command, 7 states

# System states.  These are the seven rows the RTL sequencer walks
# through; aura_pmu_pkg::power_state_e uses the same names.
add_power_state PD_TOP -domain \
  -state PS_TURBO      {-supply_expr {SS_TOP == HV} \
                        -logic_expr  {PD_CPU == RUN_HV && PD_DSP == RUN_BOOST && \
                                      PD_MEM == ACTIVE && PD_PERIPH == RUN_HV && \
                                      PD_AON == ACTIVE}} \
  -state PS_SLEEP_RET  {-supply_expr {SS_TOP == LV} \
                        -logic_expr  {PD_CPU == RETAIN && PD_DSP == DOWN && \
                                      PD_MEM == RETAIN && PD_PERIPH == DOWN && \
                                      PD_AON == ACTIVE}}

What it expresses. “The chip is in PS_TURBO exactly when PD_TOP's own supply set is at HV, and each of the five subordinate domains is in the named state listed.” Here -logic_expr references other power domains by name, compared against their own state names — no RTL signal appears in it at all.

The file's own comment (L213–214) names the stakes: these seven are the system modes the RTL sequencer walks, and aura_pmu_pkg::power_state_e uses the same identifiers. The names are load-bearing, not incidental labels.

Verified, not assumed

This composition pattern is standard, documented, intended UPF — not an idiom local to this file. Marschner's DVCon paper Unleashing the Full Power of UPF Power States carries a section under the heading “Power states of power domain PDTOP based on the power states of domains PDA, PDB”:

add_power_state PDTOP -domain \
  -state {S1 -logic_expr { PDA == RUN && PDB == RUN } } \
  -state {S2 -logic_expr { PDA == SLEEP || PDB == SLEEP } } \
  -state {S3 -logic_expr { PDA != RUN && PDB != SHUTDOWN } }

Two further things that paper establishes, both relevant to scoping:

  • The real operator set is && || == !=, including disjunction and negation. aura_top itself uses only && and == — so the reference is a subset of what the construct allows, and any model built to it should be explicit about which it targets.
  • A domain may also reference its own supply handle by FUNCTION and its own states (-logic_expr {primary == ON}, {PD != UP && PD != DOWN}). aura_top instead names the supply SET (SS_CPU == ON_HV). Both spellings occur.

The reference uses create_power_state_group zero times. Grepped and confirmed. It expresses its system modes purely as add_power_state PD_TOP -domain. That matters for the options below: the app's current Tier 2 emits a group, which is a different construct from what this file uses, not a different spelling of it.

2. Where the two-tier model falls short

The current Tier 2 emits, per Power State Table row:

add_power_state -group <TOP>_PST \
    -state { <ROW NAME> \
        -logic_expr { \
                SS_A == STATE_1 && \
                SS_B == STATE_2 \
        } \
    }

— a conjunction of supply-set state equalities, where each STATE_N is a name the generator invents by deduplicating rail combinations. Four separable gaps separate that from the reference. They are worth keeping apart, because they have different costs.

#GapEvidence
G1 Wrong object. Tier 2 attaches every system state to one global create_power_state_group; the reference attaches them to a POWER DOMAIN. Different construct, different owning object. Measured: both domain-state commands import as zero table rows plus one UNRECOGNIZED warning each — "'domain' is not modelled by this tool… a power state is attached to a supply here, never to a domain directly".
G2 No referent to name. Tier 2's terms can only be <supply set> == STATE_N. There is no per-domain named state anywhere in the app to put on the left of a term. PowerStateTableRow is (power_domain_id, state_name, net_states), and power_domain_id is used only to scope row-name uniqueness — never as a state-bearing object.
G3 A tier is missing. The reference has THREE levels: supply-set states → per-domain states → system states. The app has two. The absent level is exactly the one PD_TOP's expression is written in terms of. 5 commands / 15 states at the per-domain level; 1 command / 7 states composing them.
G4 One expression where UPF has two. 18 of 22 states carry both -supply_expr and -logic_expr; the IR silently keeps the first. PowerState.expr: Optional[str], single field. _nested_state_expr(): “Returns the first -supply_expr/-logic_expr value found”, guarded by if … and expr is None.

What is not the problem

Expression richness is not the blocker. aura_top uses only && and == — both of which Tier 2 already generates. This is an object-model gap, not a language gap: the app cannot name a domain state, not that it cannot combine terms. Saying it the other way round would point the work in the wrong direction.

3. Three options

G4 is a prerequisite for all three and is not counted against any of them.

Option A — a third tier: per-domain named states restructuring

Introduce a per-domain state entity — (power_domain_id, name, supply-set conditions, logic condition) — and make the existing Power State Table the system tier, whose rows reference those names instead of per-net values.

Table UI
Structural change. Columns become one per Power Domain rather than one per Supply Net, each cell a dropdown of that domain's own state names — plus a new editor for the per-domain states themselves. Comparable in spirit to the supply-set-scoped-rows redesign that was considered and rejected earlier, though the cell contents stay simple dropdowns.
UPF
Direct and natural: add_power_state <PD> -domain per domain, then one for the top domain composing them. Raises a real question the reference answers by omission — does create_power_state_group stay, go, or become an option?
CPF
Improves it. create_power_mode -domain_conditions {PD_CPU@RUN_HV PD_DSP@DOWN} is literally per-domain named states. The app currently has to derive that from a primary supply set's power rail — a compromise the earlier work recorded. Option A supplies the real data.
Ripples
Power State Table tab (columns, cascade, validation), Properties tables, the importer's build_power_state_table(), essentially every existing power-state test, the .pis format (a 10th state family), supported_features.
Risk
high — but it is the shape the reference has, it preserves the authored names, and it makes CPF output more correct rather than less.

Option B — extend Tier 2's expression language collapses into A

Keep the group, but allow terms of the form <PD> == <state> alongside <SS> == STATE_N.

As stated, this does not work, and it is worth saying so plainly rather than proposing it as the cheap path. The reason Tier 2 cannot express PS_TURBO is not its operator set — it is that no per-domain named state exists to reference (G2). Extending the language without introducing the referent produces a language that can name nothing. Option B therefore requires Option A's new entity, at which point it is Option A with the group retained.

One coherent variant. Derive per-domain state names automatically from the existing table: group each row's nets by which domain's supply sets use them, deduplicate, and synthesise PD_CPU == STATE_2 exactly as Tier 1 already synthesises supply-set STATE_N.

Table UI
No change at all. This is its whole appeal.
UPF / CPF
Generation-only. Produces the right shape for both, including CPF's -domain_conditions.
Cost
The names are generated, not authored: PD_CPU == STATE_2, never PD_CPU == RETAIN. For a file whose own comment says the RTL enum uses these identifiers, that is a real loss of intent. It also cannot express Layer A's -logic_expr over RTL signals (iso_en_w[2] == 0) — there is nowhere to author one.
Risk
low–medium — contained, but delivers the structure without the names, and the names are much of the value here.

Option C — carry the expressions verbatim, do not interpret them lossless, not modelled

Store both authored expressions as text — two optional fields on a small new “Domain States” table, or columns on the existing one — and re-emit them unchanged. The app never parses them.

Table UI
Minimal: two text columns, or a small side table.
UPF / CPF
Emit verbatim. Fixes the round trip completely and is the only option that handles Layer A's RTL-signal conditions honestly.
Cost
The app does not understand these states: no validation, no diagram colour, no cross-checking that a referenced state exists. It becomes a faithful text editor for this one construct.
Risk
low

The decision this actually turns on

Not “which option is best” but what C1 support is for:

  • If the goal is to author and reason about system modes the way the reference does — named per-domain states, composed, validated, reflected in the Properties tables — then Option A is the honest answer, and its cost should be accepted rather than engineered around.
  • If the goal is not losing a real file's intent on load and re-export, Option C achieves that today for a fraction of the work, and leaves A available later.
  • Option B's derived-names variant is the middle path, and its price is precise: the generated file is structurally right and its state names are this app's inventions rather than the designer's.

Worth noting that A and C are not exclusive. C could ship first as the lossless floor, with A layered on when the per-domain model is wanted — the verbatim fields then become the fallback for any expression the structured model cannot represent, which is how the app already treats several constructs it stores but does not interpret.

Flagged uncertain

  1. Whether create_power_state_group and add_power_state <PD> -domain are alternatives or complements. The reference uses only the latter; the app emits only the former. Both are real. Which one a consuming tool expects — or whether a file should carry both, as this one carries both modern and legacy state tables — is not something I could establish from the sources checked.
  2. Whether a per-domain state's supply condition may reference any associated supply set or only specific handles. PD_CPU's RETAIN conjoins SS_CPU and SS_RET, the latter being its default_retention. Whether that generalises to “any associated set” affects how constrained Option A's editor can be.
  3. Which operator subset to target. aura_top needs only &&/==; the standard allows ||/!=. A structured model that supports only the former will reject files the standard permits — a scope decision, not a technical one.
Research and proposal only. No code changed, no dialogs added, no generation logic touched. G4 — the silently discarded second expression — is a separable backend fix worth doing whichever option is chosen.
