CPF 2.0 Re-Verification

sram_power_intent.cpf re-checked against the Si2 Common Power Format specification, with sram_power_intent.upf as the golden reference for what the power intent actually is. Seventeen findings — four of them critical, and one that exists only because the file declares version 2.0.

Audited sram_power_intent.cpf (111 lines) Golden sram_power_intent.upf (139 lines) Spec Si2 CPF 2.1, 29-Dec-2014, 320 pp Findings 4 critical · 5 high · 4 medium · 3 minor · 10 confirmed correct

Read this first — what was verified against what

Two primary sources, in both directions. Findings are stated against the official Si2 CPF 2.1 specification (29-Dec-2014, 320 pp) — the real PDF, from Si2's own wp-content path via the Internet Archive — and cross-checked against the official Si2 CPF 1.0 specification (02-Jan-2007, the PDF supplied locally as Si2_CommonPowerFormat.pdf, now at docs/reference/). Every version claim below is therefore confirmed twice: present in one spec and absent from the other, rather than inferred.

The CPF 2.0 PDF itself was not obtained, and no finding depends on guessing at it. Si2 gates 2.0 and 2.1 behind a download-request form requiring name, email and company; every direct and archived URL for si2_cpf_v2.0_*.pdf returns 404 or redirects to that form, and your details were not submitted. 2.0 availability is instead read from 2.1's own two delta records — the front-matter “Enhancements and New Capabilities for CPF 2.1” (p. 9) and the per-command change log (pp. 318–320). A construct absent from both of those, but present in 2.1, was already in 2.0. Where a construct is named in them, it is flagged as 2.1-only and treated as unavailable in 2.0.

The locally-supplied PDF is Version 1.0, not 2.0. Its title page reads “Si2 Common Power Format Specification™ / Version 1.0 / 02 January 2007” — the same freely-published edition the original audit used, and the one this re-verification was set up to move off. It is not wasted: it is what makes the “CHANGED” and “RESOLVED BY 2.0” classifications below provable rather than asserted, since the question in every such case is precisely what 1.0 said.

The original 12 findings could not be recovered. Not in docs/, not among the published artifacts, not in the git history — that audit lives only in a session transcript I do not have. So items are not labelled “1 through 12”. What follows is a complete fresh audit, each item carrying the classification the task asked for. Paste the original twelve and I will map them one-for-one.

Critical

Each of these makes the file fail to parse, or silently mean something other than the golden UPF.

C1

connect_supply_net is not a CPF command — it is UPF

critical

The whole “Macro Connections” section is written in the wrong language:

connect_supply_net VDD_INT -ports {u_sram/VDD_INT}
connect_supply_net VDD -ports {u_sram/VDD}
connect_supply_net VSS -ports {u_sram/VSS}

Spec evidence connect_supply_net occurs zero times in the 320-page CPF 2.1 specification, and does not appear in the command index of §9 “General CPF Commands” (pp. 118–120). The CPF construct for this is create_global_connection:

create_global_connection -net net { -pins pin_list | -ports port_list | -pg_type pg_type_string } [-domain domain | -instances instance_list]
“Specifies how to connect a global net to the specified pins or ports. A global net can be a data net, bias net, power net or ground net.” Si2 CPF 2.1, create_global_connection, p. 129

Fix: create_global_connection -net VDD -pins {u_sram/VDD}. Note -pg_type — that is the CPF 2.0 “support of pg_type in supply net connection” enhancement, and it is the cleaner form for macro PG pins, since it connects by pin type rather than by enumerating names.

C2

Nothing is inside a power design — no set_design / end_design

critical

The file opens with set_cpf_version 2.0 and goes straight to create_power_nets. There is no design context anywhere in the file.

“Begins the definition of a power design, identified by a name that is unique among power designs within the same scope. The power intent represented by the power design is defined by the CPF commands between this command and a matching end_design command.” Si2 CPF 2.1, set_design, p. 201 — and end_design, p. 184

Consequence: every rule in the file is stated outside the scope that would bind it to the sram design. The golden UPF's equivalent framing is set_scope . plus the elaboration root; CPF expresses it structurally instead. Fix: wrap the body in set_design sram … end_design.

C3

-isolation_power_net and -isolation_ground_net do not exist

critical 
update_isolation_rules -names ISO_RULE \
    -location self \
    -isolation_power_net  VDD \
    -isolation_ground_net VSS

Spec evidence Both strings occur zero times in the CPF 2.1 specification. The command's complete documented option set is:

update_isolation_rules -names rule_list { -location {from | to | parent | self | automatic | any} | -within_hierarchy instance | -cells cell_list [-use_model -pin_mapping …] | -prefix string | -suffix string | -open_source_pins_only }… Si2 CPF 2.1, update_isolation_rules, p. 245

The isolation cell's own supply is expressed on the create command instead, via -secondary_domain:

create_isolation_rule … [-secondary_domain power_domain] Si2 CPF 2.1, create_isolation_rule, p. 134

Absent from CPF 1.0 as well — both strings occur zero times in the 1.0 specification too, so these flags exist in no version of CPF and the original audit cannot have found them legal either. Note for the record: this app's own golden.cpf uses these two flags, and the project's backend CPF parser was extended to accept them. That extension encoded a mistake: they are not CPF. Fix: name the domain whose primary supply powers the isolation cell via -secondary_domain, and drop both flags.

C4

-location self did not exist in CPF 2.0 — and the file declares 2.0

critical version-specific

This is the finding the re-verification exists to catch, and it is invisible from the 1.0 spec. The file says set_cpf_version 2.0 on line 20, then writes update_isolation_rules … -location self on line 75.

“Isolation Enhancements — Added support for location self and automatic” Si2 CPF 2.1, Enhancements and New Capabilities for CPF 2.1, p. 9
“update_isolation_rules — added –location self and –location automatic” Si2 CPF 2.1, per-command change log, p. 320

Confirmed from the other direction CPF 1.0's isolation -location admits only {from | to} — not even parent:

{ -location {from | to} … Si2 CPF 1.0, update_isolation_rules — the supplied Si2_CommonPowerFormat.pdf

So self is invalid in 1.0 and 2.0, and legal only from 2.1.

Consequence: the file is internally inconsistent — it claims a version that cannot express one of its own constructs. Two valid fixes, and the choice is a product decision: emit set_cpf_version 2.1, or map self onto a 2.0-legal location. The same applies to update_level_shifter_rules -location self, which this design does not exercise but the generator can emit. Worth noting separately: CPF 2.1 is a real, shipped version that this app does not currently offer as an export target.

High priority

The file parses, but says materially less than the golden UPF does.

H1

PD_TOP contains nothing — no -instances, no -default

high 
create_power_domain -name PD_TOP
update_power_domain -name PD_TOP -primary_power_net VDD -primary_ground_net VSS

The golden UPF says create_power_domain PD_TOP -elements {.} — the whole design root. The CPF says nothing at all about membership, so the domain selects no instances.

“-default — Identifies the specified domain as the default power domain. All instances of the current design scope that were not associated with a specific power domain belong to the default power domain.” Si2 CPF 2.1, create_power_domain, p. 160

Fix: create_power_domain -name PD_TOP -default. This is also what makes H2 unnecessary — see below.

CPF 1.0 was stricter still, which is worth knowing because it means this was never legal: 1.0 writes the three selectors as a mandatory choice group — { -default [-instances …] | -instances … | -boundary_ports … } — so a domain with none of them is a syntax error there, not merely an empty domain.

H2

The exclusion is a comment, and -exclude_instances exists

high resolved by 2.0 
#   PD_TOP excludes nested sub-hierarchy domain(s): u_sub

The generator emits this comment because it “isn't confident enough in an exact CPF equivalent to assert one”. Against CPF 1.0 that was correct — exclude_instances occurs zero times in the 1.0 specification, whose create_power_domain offers no exclusion option at all. The flag was added after 1.0, so this is a genuine resolved by 2.0 item rather than an old miss:

create_power_domain -name power_domain [-instances instance_list] [-exclude_instances instance_list] …
“Excludes those instances already selected through the -instances option. If the specified instance is not selected through the -instances option, it will be ignored.” Si2 CPF 2.1, create_power_domain, pp. 158 and 161

But read the caveat before using it. With PD_TOP fixed per H1 to -default, -exclude_instances would be ignored — nothing was selected by -instances to exclude from. And it is not needed: CPF's default-domain semantics already exclude u_sub, because u_sub is explicitly associated with PD_SUB. Correct outcome: fix H1 and delete the comment, rather than converting the comment into a flag that does nothing.

H3

-acknowledge_receiver is not the option name

high changed vs 1.0-era research 
update_power_switch_rule -name PG_SWITCH -acknowledge_receiver pwr_switch_ack
update_power_switch_rule -name string { -enable_condition_1 expression | -enable_condition_2 expression | -acknowledge_receiver_1 expression | -acknowledge_receiver_2 expression | -cells cell_list | -gate_bias_net power_net | -prefix string | … }…
“Note: If a switch rule has -acknowledge_receiver_2 specified, it must also have -acknowledge_receiver_1.” Si2 CPF 2.1, update_power_switch_rule, p. 266

The options are numbered, and paired with the correspondingly numbered -enable_condition_x. The unnumbered spelling does not appear in any 2.x syntax block.

Confirmed from the other direction CPF 1.0 has exactly the spelling this app emits — and a different argument type:

| -acknowledge_receiver pin Si2 CPF 1.0, update_power_switch_rule — the supplied Si2_CommonPowerFormat.pdf

So two things changed, not one: -acknowledge_receiver pin became -acknowledge_receiver_1 expression. The app's output is provably 1.0-shaped.

One honest complication. The spec contradicts itself here. Prose under define_power_switch_cell (p. 300) refers to “the -acknowledge_receiver option of the create_power_switch_rule command” — but create_power_switch_rule's own syntax block (p. 173) lists only -name, -domain and -external_power_net/ -external_ground_net. Resolve in favour of the syntax blocks, as this project already did once for a similar CPF inconsistency: emit -acknowledge_receiver_1 on update_power_switch_rule.

H4

The switch's control expression never reaches a construct

high

The golden UPF states the switch's control and both states:

-control_port {CTRL pwr_switch_en} \
-on_state {on VIN {CTRL}} \
-off_state {off {!CTRL}}

The CPF puts all of it in a comment:

#   PG_SWITCH: … control_port='CTRL' ack_port='ACK'
#   on_state='pwr_switch_en' off_state='!pwr_switch_en'

CPF has two real homes for this, and the spec's own worked example uses both:

create_power_domain -name X -shutoff_condition !ena -instances …
update_power_domain -name X -primary_power_net VDD_SW
create_power_switch_rule -name ps1 -domain X -external_power_net VDD Si2 CPF 2.1, create_power_switch_rule, example, p. 174
“By default, the inversion of the expression specified for the shutoff condition of the power domain is used as the driver for the enable pin of the power switch cell. For complicated cells with multiple enable pins, or if you want to use a different signal to drive the enable pins, use the update_power_switch_rule command.” Si2 CPF 2.1, create_power_switch_rule, p. 173

Fix: create_power_domain -name PD_SUB -shutoff_condition {!pwr_switch_en}, and/or update_power_switch_rule -name PG_SWITCH -enable_condition_1 {pwr_switch_en}. Without either, a CPF consumer has no idea when this domain powers down — which is the single most load-bearing fact the golden UPF carries about it.

H5

VDD_SUB is missing -internal, which the spec makes mandatory

high 
create_power_nets -nets {VDD_SUB}
“-internal — Specifies that the nets must be driven by an on-chip power switch. You must specify this option if this power net is the primary power net of an internal switchable power domain using header switches.” Si2 CPF 2.1, create_power_nets, p. 171 (and create_ground_nets, p. 132)

That is exactly VDD_SUB: it is PD_SUB's primary power net (line 48) and it is driven by the on-chip switch PG_SWITCH (line 58). The generator even labels the section “Internal Supplies (power)” — it knows the fact and does not emit it. Fix: create_power_nets -nets {VDD_SUB} -internal.

Medium

M1

set_instance . is a UPF idiom; in CPF . is the hierarchy separator

medium 
set_instance u_sub
…
set_instance .

Scoping into u_sub is correct — “If the command is specified with an instance name only, it will change the design scope” (p. 214). Coming back out is not. set_instance . occurs zero times in the spec, and:

“The supported hierarchy separators are — period (.) default; slash (/) recommended; colon (:).” Si2 CPF 2.1, Hierarchy separators, p. 44

So . is not a “root” token in CPF — it is the default separator character, and set_instance . reads as an instance literally named .. CPF restores scope structurally instead: “The scope will be restored to the scope prior to the set_instance command after the end_design” (p. 73). This finding is therefore entangled with C2 — fixing the design wrapper gives scope restoration for free.

M2

VDD_SUB is declared at the top scope, not inside u_sub

medium

The golden UPF declares it inside set_scope u_sub (line 36). The CPF declares it on line 30, before any set_instance.

“The power nets are created within the current scope.” Si2 CPF 2.1, create_power_nets, p. 171

The two files therefore place the same net in different scopes. The app already solved this for its UPF writer — nets are grouped by scope and wrapped — and the CPF writer emits every net flat at the root.

M3

OFF is modelled as 0.0 V, but -state off exists in CPF 2.0

medium reverses a 1.0-era conclusion 
create_nominal_condition -name COND_3 -voltage 0.0

This project explicitly concluded, from the CPF 1.0 spec, that “OFF is a 0.0V condition, NOT a -state off flag (CPF 1.0 defines no such option)”. That reading of 1.0 was exactly right, and 1.0 says so in as many words:

create_nominal_condition -name string -voltage float [-pmos_bias_voltage float] [-nmos_bias_voltage float]
“Note: A power domain is switched off if it is associated with a nominal condition whose voltage is 0.” Si2 CPF 1.0, create_nominal_condition — the supplied Si2_CommonPowerFormat.pdf

There is no -state option there, and no -ground_voltage either (see M4). It is not true of the version this file targets:

create_nominal_condition -name string -voltage {voltage | voltage_list} [-ground_voltage …] [-state {on | off | standby}] …
“-state {on | off | standby} — Specifies the state of a power domain when it uses this nominal condition.” Si2 CPF 2.1, create_nominal_condition, pp. 146 and 150

-state appears in neither 2.1 delta list, so it was present in 2.0. Fix: create_nominal_condition -name COND_3 -voltage 0.0 -state off. Stating the state explicitly matters — it is what tells a verification tool the domain is genuinely powered down rather than merely at a low voltage.

M4

The ground rail is never given a voltage

medium resolved by 2.0

The golden UPF states add_port_state VSS -state {ON 0.0}. In the CPF, VSS appears only as a net name and as each domain's -primary_ground_net. The nominal conditions describe the power rail alone — which is why COND_3 -voltage 0.0 (power off) is indistinguishable from a condition describing ground.

create_nominal_condition … [-ground_voltage {voltage | voltage_list}] Si2 CPF 2.1, create_nominal_condition, p. 146

Fix: add -ground_voltage 0.0 to each condition. This also narrows the gap the generated header apologises for (see L3). Another resolved-by-2.0 item: -ground_voltage occurs zero times in CPF 1.0 — a 1.0-based audit could not have raised this at all.

Minor

L1

One command per net, where -nets takes a list

minor

-nets net_list (p. 171) is list-valued. Four separate create_power_nets commands under four separate section banners is legal and semantically identical — only more verbose. Worth grouping only if the section headings are not themselves load-bearing for the reader.

L2

Nets carry no -voltage

minor

create_power_nets … [-voltage {float | voltage_range}] (p. 171) would let the rail voltages be stated at declaration as well as in the nominal conditions. Optional, and the conditions already carry the operative values — listed for completeness.

L3

The header overstates the Supply Set gap

minor 
# Supply Sets have no direct CPF equivalent -- folded into each
# domain's own primary_power_net/primary_ground_net below instead.

True as far as it goes — CPF has no supply-set construct. But the specific thing this design uses a supply set for (naming the isolation cell's own supply) does have a home: create_isolation_rule -secondary_domain, per C3. The note as written suggests more is lost than actually is.

Confirmed correct

Verified against the 2.1 syntax blocks and recorded here so they are not re-investigated.

set_cpf_version 2.0First command in the file, as required: “If specified, this command must be the first CPF command in a CPF file.” (p. 108)
create_power_nets -netsCorrect command and option for declaring power nets (p. 171).
create_ground_nets -netsCorrect for ground nets (p. 132).
create_power_domain -name -instancesBoth real options, correct spelling (p. 158). PD_SUB is well-formed.
update_power_domain -primary_power_net -primary_ground_netMatches the spec's own worked example verbatim (p. 174).
create_power_switch_rule -name -domain -external_power_netExactly the documented signature, and exactly the example on p. 174.
update_power_switch_rule -cellsReal option; the documented way to pin a specific switch cell (p. 266).
create_isolation_rule -name -from -isolation_condition -pinsAll four real; -isolation_output low is a legal value of {high|low|hold|tristate|clamp_high|clamp_low} (p. 134).
create_power_mode -name -domain_conditions -defaultCorrect, and exactly one mode carries -default: “you must define one (and only one) power mode as the default mode” (p. 168).
set_instance u_subScoping in is correct — an instance name alone changes the design scope (p. 214). Only the return trip is wrong (M1).

In classification terms:

  • Resolved by 2.0 — three items. H2, M3 and M4 each flag something a 1.0-based audit was right to call unavailable. The constructs arrived after 1.0, so these are gaps in the generator rather than errors in the original audit.
  • Changed — two items. H3's option changed name and argument type. C4 is the sharper one: -location self is legal only from 2.1, so the file's own set_cpf_version 2.0 contradicts its own content — a defect no reading of 1.0 could have surfaced, since 1.0 has neither self nor parent.
  • Still valid — eleven items. C1, C2, C3, H1, H4, H5, M1, M2 and all three minors hold identically across 1.0, 2.0 and 2.1. C3 is worth singling out: those two flags exist in no version of CPF at all, so the app's backend parser was extended to accept something that was never syntax.

New in 2.x that this generator does not use

The fresh pass the task asked for, beyond re-verifying the existing list.

  • create_global_connection -pg_type — connect macro PG pins by type rather than by enumerating u_sram/VDD, u_sram/VSS, u_sram/VDD_INT individually. Cited in the CPF 2.0 release notes as “support of pg_type in supply net connection”.
  • create_power_domain -base_domains — the CPF expression of a derived domain, closer to UPF's -available_supplies {SS_VDD} on PD_SUB (golden UPF line 69) than anything the generator currently emits. Worth evaluating; not asserted here as a like-for-like equivalent.
  • create_power_domain -driver_boundary_ports / -receiver_boundary_ports — added in 2.1 (p. 319). These are the direct counterpart of the app's own Port Attribute driver/receiver split, which currently collapses into a single -boundary_ports list. 2.1 only.
  • assert_illegal_domain_configurations — CPF has a first-class construct for stating that a domain-condition combination is illegal (p. 120). Nothing in the app produces it today.
  • CPF 2.1 as an export target. The app offers CPF 2.0 only. 2.1 is a real shipped version (29-Dec-2014) and is what makes C4's -location self legal.

Methodology. Findings are stated against the Si2 CPF 2.1 specification (29 December 2014, 320 pp, ISBN 978-1-882750-78-8), obtained as the official Si2 PDF via the Internet Archive, and cross-checked against the Si2 CPF 1.0 specification (2 January 2007, ISBN 1-882750-20-9), the locally-supplied Si2_CommonPowerFormat.pdf. Version attribution for 2.0 uses 2.1's own two delta records — the front-matter “Enhancements and New Capabilities for CPF 2.1” (p. 9) and the per-command change log (pp. 318–320): a construct absent from both, but present in 2.1, was already in 2.0. 2.1 page numbers are from the printed page footers. No CPF syntax in this report is quoted from memory or from a secondary source.
